# 豆包（aiforce.run）云端部署指南

> 适用：把本 ERP（NestJS + drizzle + PostgreSQL）部署到豆包/火山方舟等任意 Node 运行时平台。
> 本地部署见《本地部署指南.md》。本文专治云端 `xxx.aiforce.run 拒绝了我们的连接请求`（connection refused）。

---

## 0. 一句话结论

"拒绝连接" = 进程根本没有在监听端口。本工程在云端起不来，**根因有 3 个**，且都发生在"监听端口之前"：

| # | 根因 | 触发点 | 现象 |
|---|------|--------|------|
| 1 | `npm start` 入口错误（仓库根无 `main.js`） | `package.json` 的 `start` 原值 `node main.js` | 进程秒退，无任何监听 |
| 2 | 数据库不可达（`SUDA_DATABASE_URL` 仍是本机 `localhost:5434`） | `AppModule.onModuleInit → ensureRbacCatalog()` 写库失败 | 生产 `abortOnError` 中止引导，进程退出 |
| 3 | 缺 `FORCE_AUTHN_INNERAPI_DOMAIN` | lark-apaas `PlatformHttpClientService` 依赖注入即报错 | 同上，引导中止 |

**已完成的修复**：① `start` 已改为 `cd dist && node server/main.js`；② `main.ts` 视图目录做了 `dist/dist/client` / `dist/client` 双兜底；③ `build.sh` 的 lark-cli 步骤已加 `|| true` 容错。本地实测：带上下面两张环境变量后，应用成功监听 `0.0.0.0:3000` 并打印 `Server running on ...` / `API endpoints ready`。

---

## 1. 平台「构建 / 启动」命令（关键）

通用 Node 平台只会跑 `npm install` + 你指定的 build + `npm start`。**不要**用模板默认的 `npm run build`（它内含 lark-cli / 路由生成，云上易因网络失败而中断）。推荐：

- **安装**：`npm install`（已确认 `postinstall` 仅做 git hooks，无 lark-cli 依赖，云上安全）
- **构建命令**：`npm run build:prod`
  - = `build:server`（nest 编译到 `dist/server/`）+ `build:client`（vite 编译前端到 `dist/client/`）
  - 不依赖 lark-cli，linux x64 下 vite 原生绑定齐全，可成功出包
- **启动命令**：`npm start`
  - 现已修复为 `cd dist && NODE_ENV=production node server/main.js`
  - `main.ts` 会依 cwd=dist 解析视图目录（`dist/dist/client` 不存在时回退 `dist/client`），前端页面可正常渲染

> 若平台要求自定义「启动命令」字段，直接填 `npm start` 即可；若要求「运行文件」，填 `dist/server/main.js` 并 `WORKDIR=dist`。

## 2. 必须设置的环境变量（否则必 connection refused）

在平台「环境变量 / 运行时配置」面板逐项添加：

### 2.1 `SUDA_DATABASE_URL`（必填，致命）
- 指向**云端可达**的 PostgreSQL 连接串，**不能用 `localhost`**。
- 例（Supabase / RDS / Aiven）：
  ```
  SUDA_DATABASE_URL=postgres://erp_user:密码@db.xxx.supabase.co:5432/erp_db
  ```
- 为什么必填：应用启动期 `onModuleInit` 会执行 `ensureRbacCatalog()` 写入 RBAC 权限种子，连不上库就抛错；而 `main.ts` 里 `abortOnError: NODE_ENV!=='development'`（生产=true），任一启动期报错都会**中止整个引导** → 不监听 → 拒绝连接。
- 库怎么来：用云厂商托管的 Postgres，或把本地 `erp_db` 用 `pg_dump` 导出后在云上 `psql` 导入（见《本地部署指南.md》"全新机器"段落）。**注意本项目 `migrations` 不能从零建库**，必须有既有库底座。

### 2.2 `FORCE_AUTHN_INNERAPI_DOMAIN`（必填，致命）
- lark-apaas 的 `PlatformHttpClientService` 在依赖注入阶段就要求此变量，缺失即：
  ```
  ERROR [ExceptionHandler] 平台模式需要基础域名，请设置环境变量 FORCE_AUTHN_INNERAPI_DOMAIN
  ```
  同样触发 `abortOnError` 中止。
- 非飞书/豆包原生集成场景，填**任意可达 URL 占位**即可，例如：
  ```
  FORCE_AUTHN_INNERAPI_DOMAIN=https://placeholder.local
  ```

### 2.3 端口与监听地址（一般平台自动处理）
- `PORT`：平台通常自动注入（如 K8s/容器平台），`main.ts` 已 `Number(process.env.PORT || '3000')` 兼容。
- `SERVER_HOST`：默认 `0.0.0.0`（已在 `main.ts` 写死兜底），**务必对外暴露**，勿设为 `localhost`，否则外网代理同样 "拒绝连接"。

### 2.4 可选
| 变量 | 说明 |
|------|------|
| `LOG_DIR` | 日志目录，相对 cwd，需可写（默认 `./logs`） |
| `ERP_UPSTREAM_TOKEN` / `ERP_RECEIVER_ALLOWED_IPS` | 仅启用 ERP→POS 下行推送时需要 |

完整模板见仓库根 `.env.example`。

## 3. 标准部署步骤（复制即用）

1. 平台新建「Web 服务 / Node」应用，关联本仓库（或上传 `erp_source_export*.zip` 解压后的源码）。
2. **构建命令**：`npm run build:prod`
3. **启动命令**：`npm start`
4. **环境变量**：设置 `SUDA_DATABASE_URL` 与 `FORCE_AUTHN_INNERAPI_DOMAIN`（见 §2）。
5. 平台「端口」填 `3000`（或留空让 `PORT` 自动注入）。
6. 部署后观察**运行日志**：
   - 成功标志：`Server running on 0.0.0.0:xxxx` + `API endpoints ready at http://.../api`。
   - 若仍 "拒绝连接"：看日志里是否有 `平台模式需要基础域名` / `connect ECONNREFUSED` / `Cannot find module` —— 分别对应 §2.2 / §2.1 / §1 的修复未生效。

## 4. 排错速查（按日志关键字）

| 日志关键字 | 根因 | 处理 |
|------------|------|------|
| `Cannot find module 'main.js'` / `node: internal/modules/...` | `start` 没改或平台跑了 `node main.js` | 用 `npm start`（已修复为 `cd dist && node server/main.js`） |
| `平台模式需要基础域名，请设置环境变量 FORCE_AUTHN_INNERAPI_DOMAIN` | 缺环境变量 | 设置 `FORCE_AUTHN_INNERAPI_DOMAIN`（任意 URL 占位） |
| `connect ECONNREFUSED 127.0.0.1:5432` / `5434` | DB 不可达 | 把 `SUDA_DATABASE_URL` 改成云端 Postgres |
| `relation "rbac_permission" does not exist` | 库是空库、未初始化 | 用 `pg_dump` 从本地 `erp_db` 导入结构+数据，或用既有库底座 |
| `Failed to load native binding` (@swc) | 平台装依赖时丢了 swc 平台包 | 已写入 `package.json.optionalDependencies`，重装即可；或在 Docker 方案内固定 |
| 前端白屏但 `/api` 正常 | 视图目录不匹配 | 确认用 `npm run build:prod` 且 `npm start` 从 `dist/` 启动（main.ts 已双兜底） |

## 4.1 本次新增：启动自愈加固（V4 起，结构性消除"拒绝连接"）

> 背景：此前只要任一致命项没满足，进程在 `listen` 之前就崩溃 → 端口无人监听 → 浏览器"拒绝连接"，且**零日志可看**。
> V4 起做了三层加固，**保证进程无论如何都会先把端口监听起来**，把"拒绝连接"变成可诊断的运行时报错：

| 加固点 | 改动 | 效果 |
|--------|------|------|
| ① `postinstall` 容错 | `fullstack-cli action-plugin init` 后加 `\|\| true` | 云端 `npm install` 不因平台 CLI 拉取/网络失败而整体中断（否则无 node_modules、start 直接失败） |
| ② 平台域名兜底 | `main.ts` 启动最早处 `process.env.FORCE_AUTHN_INNERAPI_DOMAIN ??= 'https://placeholder.local'` | 未配该变量也不会在依赖注入阶段崩溃 |
| ③ RBAC 种子非致命 | `AppModule.onModuleInit` 的 `ensureRbacCatalog()` 包 `try/catch`，失败仅告警 | DB 暂不可达时不再中止引导，端口照常监听；DB 相关接口运行时返回明确错误 |

**本地实测**（两个变量一个都不设、DB 指向不存在的端口）：进程打印 `Server running` + `API endpoints ready`，端口可探测（HTTP 500/502，而非"拒绝连接"）。
**结论**：V4 之后，凡属"进程起不来"类的问题都已消除；若预览仍异常，必定是**运行时**问题（DB 连接串错误/库未初始化/构建未出前端），按 §4 日志关键字即可定位。

## 5. 备选：Docker 部署（最稳，绕过平台构建契约）

若平台支持 Docker / 自定义运行时，用仓库 `Dockerfile`（见同目录）可完全自控构建与启动，避免 lark-cli、脚本契约等不确定因素。构建时同样需要传入 §2 的两个必填环境变量。

## 6. 已落地代码改动（本次修复）
- `package.json`：`"start"` 由 `node main.js` → `cd dist && NODE_ENV=production node server/main.js`。
- `server/main.ts`：视图目录 `dist/dist/client` → 增加 `dist/client` 兜底（`existsSync`）；启动最早处给 `FORCE_AUTHN_INNERAPI_DOMAIN` 兜底占位。
