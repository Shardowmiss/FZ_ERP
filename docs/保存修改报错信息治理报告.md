# 保存/修改报错信息治理报告

> 目标：消除「保存失败」「删除失败」这类笼统、粗暴的报错——业务人员会误以为系统出故障，运维也无法从文案定位问题。
> 改法分两层：①后端把数据库约束冲突翻译成**具体中文 + 正确 HTTP 状态码**；②品牌改名增加**业务层主动校验**；③前端统一透出后端具体消息，并补齐此前漏掉的 `toast.error('X失败')` 形式。

---

## 一、根因（两层叠加）

| 层 | 原实现 | 后果 |
|----|--------|------|
| 后端过滤器 | `GlobalExceptionFilter` 把 23503/23505/23514/23502 等约束冲突一律当 500「服务器内部错误」抛给前端 | 所有「被引用/重复/必填为空/不满足规则」都变成「服务器内部错误」 |
| 前端 catch | 各页面 `catch` 后硬编码 `toast('保存失败')`，把 `error.response.data.error.message` 直接丢弃 | 即使后端未来返回了具体消息，前端也显示不出 |

**结论**：两层一起改才能真正见效——后端负责“说清楚”，前端负责“透出来”。

---

## 二、后端改造

### 2.1 约束冲突翻译器（新增 `server/common/errors/db-constraint.ts`）
把 Postgres 驱动抛出的约束错误，按 SQLSTATE 翻译成业务可读中文。

| SQLSTATE | 含义 | 响应码 | HTTP | 翻译文案（示例） |
|----------|------|--------|------|------------------|
| 23503 | 外键冲突（被引用 / 非法外键值） | `CONFLICT` | 409 | `该数据已被「款号」引用，不允许删除或修改` |
| 23505 | 唯一约束冲突 | `CONFLICT` | 409 | `数据已存在（brand, NIKE），请勿重复` |
| 23514 | 检查约束冲突 | `VALIDATION_ERROR` | 422 | `数据不满足业务规则约束（chk_xxx），请检查填写内容` |
| 23502 | 非空约束冲突 | `VALIDATION_ERROR` | 422 | `必填字段「supplier_id」不能为空` |
| 22P02 | 非法类型（多为非法 UUID） | `NOT_FOUND` | 404 | `资源不存在`（原有逻辑，未变） |
| 其它/未知 | — | `INTERNAL_ERROR` | 500 | `服务器内部错误`（保留 requestId 兜底，未变） |

- `TABLE_LABELS`：外键引用表 → 中文业务名（supplier→供应商、style→款号、garment_purchase_order→成衣采购单 等 40+ 张表）。未登记的表回退为原表名。
- `CONSTRAINT_FRIENDLY`：已知约束名 → 精确文案（如 `style_brand_code_fkey`、`gpo_brand_code_fkey`、`payable_supplier_id_fkey`）。后续新增主数据外键时在此登记即可获得更友好、稳定的报错。

### 2.2 过滤器接线（修改 `server/common/filters/exception.filter.ts`）
在 `22P02` 分支之后新增分支：带 `.code` 的数据库错误 → 调 `translateDbConstraintError()`；
命中则降级为 4xx 并记 **info** 日志（便于运维按约束名/表名检索），未命中仍按 500 但保留 `sqlState`。
> ⚠️ 历史教训：上一轮改造只加了 import 却漏接该分支，约束错误仍走 500；本轮已用过滤器级单测锁定接线。

### 2.3 品牌改名主动校验（修改 `server/modules/base/style-attribute/style-attribute.service.ts` 的 `update()`）
因回滚后 `style.brand` 是自由文本列、`style_attribute` 表无外键，改名冲突**无法**靠 23503 触发，故在业务层主动校验：
```ts
if (current.attrType === 'brand' && data.attrName.trim() !== current.attrName) {
  const refCount = await db.select({ c: count() }).from(style)
    .where(eq(style.brand, current.attrName));
  if (refCount > 0) {
    throw new BusinessException(ResponseCode.CONFLICT,
      `该品牌名称「${current.attrName}」已被 ${refCount} 个款号引用，不允许修改。请先处理相关款号后再改名。`);
  }
}
```
→ 直接命中用户举例：“该品牌名称已被别的地方引用，不允许修改”。
（`remove()` 删除品牌时若被款号引用，已改为**禁用**而非报错，文案“该属性已被款号引用，已改为禁用状态”。）

## 三、前端改造

### 3.1 提取助手（新增 `client/src/utils/errMsg.ts`）
```ts
export function errMsg(e: unknown, fallback = '操作失败'): string {
  const serverMsg = e?.response?.data?.error?.message;
  if (serverMsg?.trim()) return serverMsg;
  if (e?.message?.trim()) return e.message;
  return fallback;
}
```

### 3.2 页面透出（批量改造）
- 此前 50 个页面的 `toast('保存失败'/'删除失败'/'更新失败'/'提交失败'/'操作失败')` 已改为 `toast(errMsg(e, '原文案'))`（前序会话完成）。
- **本轮补齐遗漏**：扫描发现还有 38 个页面使用 `toast.error('X失败')` 或 `toast('X失败')` 形式（`toast.error` 方法调用 + 裸 `toast`），此前脚本只改了 `toast('...')` 形式，漏掉了这批。本轮一并改为 `toast(.error)(errMsg(var, 'X失败'))`，并对 `catch {` 无绑定块补成 `catch (e) {`。覆盖文案含：保存失败、删除失败、**审核失败、作废失败、导出失败、生成失败、排序失败**。

| 模块 | 代表页面 |
|------|----------|
| 基础资料 | StyleAttributePage、StyleAttrDefPage、ColorGroup、SizeGroup、Supplier、Warehouse、Store、Material、Sku… |
| 采购 | PurchaseOrder(Page/Edit)、PurchaseInbound、PurchaseReturn、GarmentPurchase*(Order/Inbound/Return)… |
| 销售 | SalesOrder(Page/Edit/Modal)、SalesOutbound、SalesReturn |
| 生产 | WorkOrder、MaterialIssue、MaterialPurchase*、FinishReceipt、Bom |
| 库存 | InventoryTransfer、InventoryStocktake、Inventory*Query/Outbound/Inbound、Barcode、Replenish… |
| 财务 | Payment(Page/Edit)、Receipt(Page/Edit)、Payable、Receivable、Profit、MonthClose |
| 展会/零售/委外/会员/系统 | TradeShow、PreOrder、Allocation*、RetailOrder/Return、Subcontract、Member、SystemConfig、RoleManage、CodeRule |

> 现状：`client/src` 下 **零** 残留硬编码 `toast(.error)?('X失败')`；成功类文案（X成功）保持不变。

## 四、Before / After 对照

| 场景 | 改造前 | 改造后 |
|------|--------|--------|
| 修改品牌名（被款号引用） | 前端 `保存失败` | `该品牌名称「耐克」已被 1 个款号引用，不允许修改。请先处理相关款号后再改名。` |
| 删除被引用的供应商 | 500「服务器内部错误」 | 409 `该供应商已存在应付单据，不允许删除` |
| 重复编码 | 500「服务器内部错误」 | 409 `数据已存在（brand, NIKE），请勿重复` |
| 必填为空 | 500「服务器内部错误」 | 422 `必填字段「supplier_id」不能为空` |
| 审核/作废单据失败（后端有具体原因） | `审核失败`/`作废失败` | 透出后端具体原因（如 `该单据已审核，不允许重复操作`） |

## 六、运维定位建议
- 约束类拒绝记 **info** 级 `db.constraint` 日志，含 `code`/`message`/`details(constraint=...)`，可直接按约束名反查。
- 未知 500 记 `error` 级 `unhandled` / `db.error`，含 `requestId` 与 `sqlState`，工单附 requestId 即可捞全上下文。

## 七、后续可优化（非阻塞）
1. `CONSTRAINT_FRIENDLY` 随新外键持续补登，文案越具体越好。
2. 字段级校验（class-validator）消息已归集为 `fieldErrors`，可进一步在表单逐项标红。
3. 预存的 `month-close.service.ts` 与 `promotion-push.spec.ts` 类型错误建议单独排期清理。
